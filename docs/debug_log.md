## 2026-10 · 「更强」的配置反而更差：0.9227 < 0.9268

**现象**

在基线（宏 AUC 0.9268）之上，尝试了一组看起来更"高级"的配置：

| 改动 | 预期 | 实际 |
|---|---|---|
| 换更强预训练 `ra4_in1k` | 更好 | — |
| dropout 0.3 → 0.5 | 抑制过拟合 | — |
| 分层学习率（骨干小、头部大） | 更好 | — |
| 更强增强 | 更好 | — |

**组合结果：验证宏平均 AUC 0.9227，低于基线的 0.9268。**

**原因**

在 1545 张训练图、221 张验证集的规模上：

- dropout 0.5 对这个数据量**过强**，模型欠拟合
- 更强增强同样加剧欠拟合
- 预训练权重换强带来的收益被上面两项抵消

**处理**

回到基线配置（`ra + dropout 0.3 + 统一学习率`），
改进版配置保留在 `configs/config_exp2_reg.yaml` **备查**，不删除。

**验证**

基线 0.9268 > 改进版 0.9227，差 0.0041。

**现状**

✅ 已定论。**这条记录的价值在于**：它证明"加复杂度"不等于"涨点"，
而且保留失败配置供复查，比删掉更专业。

## 2026-10 · 稀有标签「AUC 高、F1 低」

**现象**

逐标签看，`CRVO` 的 AUC = **1.000**，但 F1 很低；`ODP`、`OTHER` 同时是 AUC 最低的两个（0.805 / 0.789）。

**原因**

正例数太少：

| 标签 | 训练集正例 | 说明 |
|---|---|---|
| DR / NORMAL | 346 | 多数类 |
| CRS | 21 | 最稀有 |
| ASR | 23 | |
| HTR | 24 | |
| CSR | 25 | |

正例只有 3~6 张的标签，模型**排序能力可以很好（AUC 高），
但在固定 0.5 阈值下几乎不会报正**——训练时正负差太悬殊，偏置偏向负类。

所以"AUC 1.000 + F1 很低"不是矛盾，而是**稀有类在固定阈值下的必然表现**。

**处理**

- 主指标改用**宏平均 AUC**（与阈值无关），而不是 F1
- 逐标签表里**同时输出正例数**，让读者能判断 F1=0 是模型问题还是样本问题
- `pos_weight` 设上限 20，避免稀有类主导梯度

**验证**

README 里明确写出"稀有标签普遍呈现 AUC 高、F1 低的形态"。

**现状**

⚠️ **已知边界**。真正的解法是**逐标签阈值搜索**，
已在 README 中列为后续方向，本次未做。

## 2026-10 · `pos_weight` 不设上限会到 70

**现象**

最初直接用 `neg / pos` 作为 BCE 的正类权重，训练不稳定。

**原因**

最稀有的 `CRS` 只有 21 个正例，1545 张训练图：

```
(1545 - 21) / 21 ≈ 72.6
```

单个标签的权重是多数类的 72 倍，梯度会被这一个标签主导，
其余 19 个标签几乎学不动。

**处理**

`compute_pos_weight(y, cap=20.0)`，用 `np.minimum(w, cap)` 截断。

**验证**

权重分布被压进 [1, 20] 区间，训练恢复正常。

**现状**

✅ 已解决。`pos_weight_cap` 也外置到 `config.yaml`，方便按数据集调整。

## 2026-10 · fp16 混合精度训练出现 NaN

**现象**

开启 AMP 后，部分轮次 loss 变成 `NaN`。

**原因**

fp16 的动态范围窄（最大约 65504），BatchNorm 的权重在训练早期可能出现
极端值，`fp16` 下直接溢出成 `inf`，反传后变成 `NaN`。

**处理**

`amp_dtype: bf16`。bf16 的尾数位少（精度低）但**指数位与 fp32 相同**，
动态范围足够大，不会因为 BN 权重极端而溢出。

**验证**

改 bf16 后训练全程无 NaN。

**现状**

✅ 已解决，配置项保留在 `config.yaml` 并附注释说明原因。

## 2026-10 · RTX 50 系显卡报 `no kernel image is available`

**现象**

在 RTX 5060 Laptop 上运行报错：

```
RuntimeError: CUDA error: no kernel image is available for execution on the device
```

**原因**

RTX 50 系是 **Blackwell 架构（sm_120）**，而旧版 torch 的 CUDA 内核只编译到
sm_86 / sm_89，没有 sm_120 的 kernel 镜像。

**处理**

安装 **CUDA 12.8 及以上**对应的 torch（本项目用 `torch 2.11.0+cu128`）。

**验证**

`torch.cuda.is_available()` 为 True，训练正常运行。

**现状**

✅ 已解决，写进 README 常见问题。

## 2026-10 · Windows 上 DataLoader 报错

**现象**

`num_workers > 0` 时 DataLoader 抛异常或长时间无输出。

**原因**

Windows 用 `spawn` 方式启动子进程，DataLoader 的 worker 需要重新 import 主模块。
如果 `if __name__ == "__main__"` 保护不当，或数据集对象持有不可 pickle 的成员，
就会失败。

**处理**

把 `config.yaml` 的 `train.num_workers` 改成 `0`（主进程加载）。

**验证**

改 0 后正常。

**现状**

✅ 有兜底方案。注意 `num_workers=0` 会慢一些，
这也是"跨平台可复现"要付出的代价之一。

## 2026-10 · 测试集没有标签，无法本地评估

**现象**

`test.csv` 只有 `path` 列，没有 20 个标签列。

**原因**

这是课程竞赛式提交安排——测试标签不在本地，由评测端计算。

**处理**

- 评估只在 **val** 上做，README 明确写明"test.csv 无标签，无法本地评估"

**验证**

提交文件格式与 `sample_submission.csv` 对齐（20 列概率）。

**现状**

⚠️ **流程限制**，不是 bug。**注意不要在报告里写"测试集 AUC"**——那是错的，
本地只有验证集数字。

## 2026-10 · Hamming 91.70% 容易被读成「准确率很高」

**现象**

结果表里同时有：Hamming 正确率 91.70%、微平均 F1 54.64%、宏平均 AUC 0.9268。

**原因**

20 个标签、正例占比很低的场景下：

- **Hamming** 逐元素比较，负类占绝大多数 → 全预测 0 也能到 80%+
- **F1** 只看正类，稀有类拉低整体 → 54.64%
- **AUC** 与阈值无关 → 0.9268

三个数都对，但**只有 AUC 适合当主指标**。

**处理**

- `README` 把宏平均 AUC 明确标为"主指标"
- `docs/workflow.md` 里专门写了一张"三条口径不能混"的表
- 引用指标时必须带名字，不能只说"准确率"

**验证**

—

**现状**

⚠️ **表述风险**，不是技术问题。但这是最容易被面试官或评审问住的地方。
